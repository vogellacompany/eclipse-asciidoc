= AsciiDoc Editor Features
vogella GmbH
:toc:

This document describes what the AsciiDoc editor in this repository supports.
Everything listed here is implemented and covered by tests in `tests/com.vogella.asciidoc.lsp.server.tests`.

== Editor and content type

Files with the `.adoc` or `.asciidoc` extension are bound to the content type `com.vogella.asciidoc.contenttype` and open in the AsciiDoc editor.

The editor has two tabs.
`Source` is the Eclipse generic editor, so syntax highlighting comes from the TM4E grammar and all language features come from the language server through LSP4E.
`Preview` renders the document to HTML and refreshes 500 ms after you stop typing.

== Preview

The preview is produced by a small renderer written in plain Java inside the language server bundle.
There is no AsciidoctorJ, no JRuby and no external process.
The editor asks for it through a custom LSP request, `asciidoc/preview`.

Supported block syntax:

* Headings from `=` to `======`, with an id taken from a preceding `[[id]]` or `[#id]` line, otherwise generated from the title.
* Paragraphs, with a trailing `+` turning into a line break.
* Attribute entries (`:name: value`) and their substitution as `{name}` in text.
An unknown `{name}` is left as written.
* Source and listing blocks (`----`), literal blocks (`....`), example blocks (`====`), sidebars (`****`) and quote blocks (`____`).
A `[source,lang]` attribute line adds a `language-lang` class.
* Admonitions, both as a paragraph (`NOTE: text`) and as a block with a preceding `[NOTE]` line.
* Tables (`|===`), with the first row rendered as a header when it is followed by an empty line or the block carries `[options="header"]`.
* Unordered, ordered and description lists, including nesting and `* [x]` checkboxes.
* Block images (`image::target[]`) and includes (`include::target[]`).
* Comments (`//` and `////`), thematic breaks (`'''`) and page breaks (`<<<`).

Supported inline syntax:

* `*bold*`, `_italic_`, `` `mono` ``, `#highlight#`, `^super^`, `~sub~` and `+literal+`.
* Bare `http://` and `https://` URLs, `link:target[text]`, `xref:target[text]` and `<<target,text>>`.
* Inline images (`image:target[]`).
* `kbd:[Ctrl+S]`, `btn:[OK]` and `menu:File[Save]`.

Images are resolved against the document directory joined with the `imagesdir` attribute.
PNG, JPEG, GIF, SVG and WEBP files up to 10 MB are embedded as `data:` URIs, because `Browser.setText` has no base URL and cannot load `file://` resources on every platform.
Larger files fall back to a `file:///` URL, and a missing file renders an inline error instead.

Includes are resolved in place, with a depth limit of ten and cycle detection.
An open editor wins over the file on disk, so an included document that you are editing shows its unsaved state.

Clicking a link in the preview opens `.adoc` targets in Eclipse and `http`/`https` targets in the external browser.

Out of scope for the renderer: footnotes, callouts, `ifdef::` and friends, passthrough blocks, nested tables, list continuation, the `lines=` and `tag=` include filters, and backslash escaping.
Anything the renderer does not know renders as a plain paragraph and never throws.

== Diagnostics

Diagnostics are published on open and on every change, and cleared when the document is closed.
Every diagnostic carries the source `asciidoc`.

[cols="3,1"]
|===
|Check |Severity

|`include::` target does not exist
|Error

|`image::` or `image:` target does not exist, resolved through `imagesdir`
|Warning

|`<<id>>` or `xref:id[]` with no matching anchor or heading id in the document
|Warning

|Duplicate anchor id
|Warning

|`xref:file.adoc[]` or `link:file.adoc[]` target file does not exist
|Warning
|===

== Content assist

The trigger characters are `<`, `{`, `:` and `/`.

* At the start of a line: snippets for admonitions, `image::`, `include::`, a source block, a table, a block title and headings.
* After `image::` or `image:`: image files from the directory that `imagesdir` points at, or from the document directory when no `imagesdir` is set, filtered by what you have typed.
* After `include::`, `link:` or `xref:`: `.adoc` files and subdirectories relative to the document, so you can walk into a folder one segment at a time.
* After `<<` or `xref:`: every anchor id and heading id in the document, with the heading title as the detail.
* After `{`: every attribute defined with `:name:` in the document.

== Navigation

* *Document links*: `include::`, `image::`, `image:`, `link:`, `xref:` to another `.adoc` file, and bare `http`/`https` URLs.
* *Go to definition*: `include::` targets, `image` targets, `<<id>>` and `xref:id[]` to the anchor or heading in the same document, and `xref:file.adoc#id[]` to the heading in another file.
The other file is read from the open editors when possible, otherwise from disk.
* *Hover*: a preview of the image behind an `image` macro, and the level and title of the heading behind a cross reference.
* *Outline*: the section hierarchy, nested by heading level.
A line that looks like a heading inside a delimited block is not treated as one.
* *Folding*: one range per section, one per delimited block, and comment blocks folded as comments.

== Not implemented

Semantic tokens, rename, find references, formatting, code lenses, workspace symbols, `ifdef`/`ifndef`, a cross document anchor index and spell checking are all out of scope.
Syntax highlighting is deliberately left to the TM4E grammar rather than LSP semantic tokens.

== Architecture

* `com.vogella.asciidoc.editor`: content type, TM4E grammar, language configuration and the two tab editor.
* `com.vogella.asciidoc.lsp.server`: the LSP4J language server and the HTML renderer, with no dependency on Eclipse.
* `com.vogella.asciidoc.lsp.client`: the LSP4E registration and the connection provider.

The server runs in the same JVM as the IDE.
The connection provider wires it to LSP4E over piped streams and creates a fresh server instance on every start, so a restart never inherits stale state.
